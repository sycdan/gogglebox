# Agent Onboarding

You have been hired to work on Gogglebox: a LAN-first Jellyfin household
frontend. Express API + React/Vite client, TypeScript throughout. Backend entry
`src/server/server.ts`, client `src/client/App.tsx`, config
`src/server/config.ts`, Jellyfin client `src/server/jellyfin.ts`.

## Run everything in Docker (host stays minimal)

The host needs only Docker + git. All app execution goes through Compose, and
every stack is the self-host stack in `deploy/docker-compose.yml` with layers on
top. Deps live in a named `node_modules` volume, never installed on the host.
Always go through a wrapper script; it supplies the variables deploy requires.

- `./scripts/e2e.sh …` layers `docker-compose.e2e.yml`: the production image
  built from this checkout, a seeded offline sandbox Jellyfin (`.env.sbx` +
  `config.sbx.json`, both generated; see `tools/sandbox/README.md`), `proof`,
  and `check`/`test`. CI runs exactly this.
- `./scripts/dev.sh …` adds `docker-compose.dev.yml`: the same stack with the
  app bind-mounted and hot-reloading (`tsx watch` + a Vite `client`).

```bash
./scripts/e2e.sh run --rm check   # typecheck (no Jellyfin)
./scripts/e2e.sh run --rm test    # unit tests (no Jellyfin)
./scripts/dev.sh up -d            # hot-reload app on the sandbox
PROOF_FLOW=mark-all-watched ./scripts/dev.sh run --rm proof
```

Bootstrap the sandbox once as README "Development" describes. Bare `up -d` skips
the one-shot `tools`-profile services (`sandbox-generate`/`provision`/`reset`);
run those explicitly with `run --rm`.

The proxy is the **single entrypoint**, the same-origin front door at
`http://localhost:8080` (`/api` → gogglebox, `/player` → Jellyfin, `/` →
gogglebox, or the Vite client under dev.sh). `/player` is a Gogglebox proxy
mount: Caddy strips it before forwarding to the normal Jellyfin origin from
`JELLYFIN_URL`. Serving everything from ONE origin lets the gbx client seed
Jellyfin-web's localStorage so the `/player` tab auto-logs-in as the per-party
JF user. The app binds **no host port** — reach it only through the proxy.

### Env

deploy's `${VAR:?required}` values are interpolated at parse time, before any
layer applies, so `scripts/e2e.sh` passes `--env-file .env.e2e` (committed
placeholders) and then `.env.sbx` (generated by provisioning: the minted
Jellyfin API key and the auto-login `ACCESS_TOKEN`), later file winning. The
default `.env` is not read.

### Jellyfin

The app (and `proof`) need the provisioned sandbox Jellyfin. The server exits at
startup if Jellyfin is unreachable. `check`/`test` need no Jellyfin.

### Vite cache / blank-SPA recovery

The client's Vite dep-optimizer cache (`cacheDir`) is on an ephemeral tmpfs
(`/tmp/vite`), not the persistent `node_modules` volume, so a stale/half-written
`.vite` can't survive a kill and wedge the next boot with 504s. If the client
ever serves a blank SPA, recover with
`./scripts/dev.sh up -d --force-recreate client` (NOT `restart`, which races the
optimizer).

### Visual proof

The Playwright suite entry is `e2e/run.mjs`. It logs in, then runs one module
per flow under `e2e/flows/`, with shared harness/session/viewer helpers under
`e2e/lib/`. It writes PNGs to `./artifacts/<timestamp>/` for a single flow. When
running several flows as one prover pass, set the same `PROOF_RUN_ID` on every
invocation so screenshots are grouped under
`./artifacts/<PROOF_RUN_ID>/<timestamp-flow>/`. The prover Reads those PNGs to
confirm the UI.

The `player-handoff` flow (Stage A browser auto-login) MUST run against the
same-origin proxy so the localStorage origin matches `/player`. `proof` targets
the proxy (`PROOF_URL=http://proxy:8080`) by default:

```bash
./scripts/dev.sh run --rm -e PROOF_FLOW=player-handoff proof
```

It opens a new tab at `/player/web/...` and writes `player-handoff-gbx.png` (the
gbx launch panel) + `player-handoff-jellyfin-loggedin.png` (the Jellyfin tab,
which must show the logged-in home/library and NO manual login form).

## Generating a UUIDv7

Whenever any workflow step below calls for a fresh UUIDv7 (e.g. `prompt_id`,
a proof-link filename, etc.), generate it with
`./scripts/e2e.sh run --rm deps npx uuidv7` (the `uuidv7` package is already a
project dependency, so `npx` resolves it locally with no network fetch). Use
`deps` directly, not `check`/`test` — those depend on `deps` completing first,
so routing through them pays for a redundant `npm ci` wait on every call.
Never hand-pick or reuse a UUIDv7.

## Conventions

- Never break the config schema. Any older `config.json` must roll forward to
  the current shape — extend the `schemaVersion` migration chain in
  `src/server/config.ts` so startup auto-migrates from _any_ prior version.
  Never require a manual migration step, never drop support for an old version.
- Keep `README.md` current when project direction, user-facing behavior,
  deployment shape, major workflows, or other human-important project context
  changes. The README is for humans: capture high-level positioning, shipped
  capabilities, practical usage, and roadmap pointers, but do not dump low-level
  implementation detail there.
- Never run `npm`/`node`/`tsc` on the host — use the compose services above.
- If a `docker run` ever needs an absolute in-container path under Git Bash,
  prefix with `MSYS_NO_PATHCONV=1` to stop path mangling. (Plain
  `docker compose ... run` commands above don't need it.)
- Don't commit `artifacts/` (gitignored) — it's run output.
